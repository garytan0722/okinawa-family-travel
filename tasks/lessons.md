# Lessons

- Never place real booking codes, access links, PINs, or private accommodation names in source code—even as denylist test fixtures. Test privacy through schema rules and generic public labels, then scan and purge Git history before publication.
- A successful Pages deployment and fresh-browser QA do not prove that existing PWA clients update. Test the upgrade path from the previous service-worker cache; revision shell assets, prefer network for online navigations, and explicitly trigger worker update/takeover.
- When the user freezes a date range, protect the complete serialized day objects with regression hashes and derive any new summary UI from separate confirmed data. Before replacing earlier attractions, compare them against the frozen segment and exclude cross-segment duplicates.
- When the user corrects confirmed logistics inside an otherwise frozen date range, treat that correction as a narrow exception: update every dependent timeline, keep unrelated activities unchanged, and refresh the regression hashes only after reviewing the exact day-object diff.
- When increasing a completion stamp, grow the visual mark, hit target, and card text clearance together; verify both unchecked and checked states at the narrowest supported width so the emphasis does not obscure itinerary content.
- When correcting a group departure date, update the flight record, fixed event, party period, stay labels, every variant's dependent day plan, and generated PDFs as one atomic change; remove stale split language everywhere instead of patching only the flight card.
- Treat user-provided traveler labels as exact strings: lock the corrected spelling in tests, assert the superseded spelling is absent from public artifacts, and rotate the PWA cache so phones do not retain the typo.
- When the user identifies the booked operator's official site, replace the superseded operator name and source atomically across fixed events, every variant, render tests, PDF verification, and the PWA cache. Distinguish an advertised activity time from the operator's earlier mandatory meeting time and surface both prominently.
- When a user names a place phonetically or with a typo, resolve it to the official venue and confirm the identity before editing. Once confirmed, preserve the exact official name, the user's original Maps link, and the requested replacement relationship in tests.
- Restaurant recommendations must be route-aware, not merely family-friendly: verify each meal sits between the preceding and following stops, eliminate avoidable backtracking, and keep frozen travel days byte-for-byte unchanged unless the user explicitly corrects them.
- Validate backup restaurants against the same stop order as the primary choice; a backup located beyond the next attraction can quietly reintroduce backtracking even when the primary route is correct.
- Do not equate HTTP 200 or a successful fresh-browser render with real-device availability. For a public PWA, provide a same-origin recovery path that can remove only the app's stale caches and workers while preserving local itinerary records, and verify the existing-client path separately.
- A daily route must be validated as a complete ordered journey, not merely as valid Maps URLs: include the previous night's stay as origin, tonight's stay as destination, retain concrete walk destinations, show every stop in the UI, and split only at the platform limit with an overlapping handoff. For private lodging, publish only a broad public-area anchor and keep the listing URL and exact address out of source control.
